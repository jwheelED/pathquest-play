Live Lecture Reliability — Decision Guide

Two issues to resolve: slow MCQ preparation (~90s) and Deepgram chunking that splits long questions. Walk through the diagnostics, pick remediations, get a sequenced plan.

    1. What we're deciding

    You face two independent reliability problems with the live lecture capture pipeline. This guide walks each one through diagnostics → remediation options → a recommended order of operations.

    Issue A — MCQ "preparing" stalls ~90s

    From the moment passive detection picks up a question to the moment students see four options, ~90 seconds elapse.

    Hot path: src/hooks/usePassiveQuestionDetection.ts → supabase/functions/generate-mcq-options/index.ts → Lovable AI Gateway → Gemini.

    Issue B — long questions get split

    Sentences like "If a cell has a high surface-area-to-volume ratio, what advantage does that give it?" never arrive at the detector as a single utterance — Deepgram finalizes mid-sentence on the breath pause.

    Hot path: Deepgram WSS → relay → src/lib/deepgramStreaming.ts → checkUtterance().

    These two issues are independent. Fixing one does not fix the other. You can ship them on separate branches.

    2. Issue A — root-cause hypotheses, ranked

    Read top-down. The first two are likely most of your 90 seconds.

    Smoking gun (high confidence): supabase/functions/generate-mcq-options/index.ts:271 references the model string 'google/gemini-3.5-flash'. There is no such model — Gemini went 1.5 → 2.0 → 2.5. This path either 404s through the Lovable gateway (forcing an error fallback) or is silently routed to a slow default. Either way it is broken as intended.

    Hypotheses

    1. Sequential double-call to slow model. callModel(primaryModel) at line 273, then if the deterministic validateAnswer() rejects (lines 295–317), a second callModel('google/gemini-2.5-pro', verdict.reason). Two sequential 2.5 Pro tool-calls with 6 KB transcript context = 40–80 s easily.
    2. Wrong/nonexistent model name in fast-path branch. When focusedContext.length <= 80 (rare in live use), the code asks for gemini-3.5-flash. Gateway 404 → retry/timeout latency on top of whatever fallback fires.
    3. Cold-start of the edge function. Supabase edge functions cold-start in 100–500ms; not 90s on its own, but contributes 0.5–2 s when the function hasn't been hit in a while.
    4. No request timeout / abort signal. If Gemini stalls, there's no client-side circuit breaker. The UI sits on "preparing" until the function returns or its 60s timeout fires.
    5. No streaming. The endpoint returns only after the full tool call completes. Even a fast model with streaming would feel faster.
    6. Validator runs after full generation. Strict but expensive: the wrong-letter check forces a full second pass on the slowest model.

    3. Issue A — diagnostic steps (cheap, do first)

    Don't pick a fix until you've confirmed which hypothesis is the actual bottleneck. These take under an hour combined.

    D1. Add timing logs around the LLM calls

    Wrap each callModel(...) in performance.now() and log the model used, request size, response time, and whether validation passed:

    const t0 = performance.now();
const response = await callModel(primaryModel);
console.log(JSON.stringify({
  evt: "mcq.primary_call",
  model: primaryModel,
  ms: Math.round(performance.now() - t0),
  focused_ctx: focusedContext.length,
  broad_ctx: broadContext.length,
}));

    Then re-deploy and run a single live capture. The logs in the Supabase Functions dashboard will tell you exactly where the 90 s went.

    D2. Re-run with the typo fixed first

    Change line 271 from 'google/gemini-3.5-flash' to 'google/gemini-2.5-flash' (or whatever Lovable exposes) and measure again. If MCQ latency drops, the typo was masking a real fallback storm.

    D3. Force the fast path and measure

    Temporarily set primaryModel = 'google/gemini-2.5-flash' unconditionally and measure. If 2.5 Flash returns in 5–10s, the bottleneck is the model choice on the "I have context" branch.

    D4. Inspect validator rejection rate

    Count console.warn("MCQ validator REJECTED ...") hits per session. If >30%, every other question pays the second-call tax — making the validator itself the bottleneck on average.

    4. Issue A — remediation options

    Pick one or more. The effort/risk/expected-gain pills are calibrated to this codebase, not generic.

    R1. Fix the model-name typo

    Effort: 5 min Risk: trivial Gain: unknown until measured

    Change 'google/gemini-3.5-flash' → 'google/gemini-2.5-flash'. Possibly a no-op (if the gateway already silently rerouted), possibly a 60s win. Do it regardless.

    R2. Swap default model: 2.5 Pro → 2.5 Flash

    Effort: 15 min Risk: MCQ quality may drop on long-context questions Gain: 3–6× latency cut

    Use gemini-2.5-flash as the primary in both branches. Reserve gemini-2.5-pro for the retry path only (when the validator rejects). Most questions don't need Pro-level reasoning.

    R3. Add request timeout + user-visible fallback

    Effort: 30 min Risk: low Gain: bounds worst case, doesn't fix average

    Wrap the fetch in an AbortController with a 20 s ceiling. If it fires, surface a "Send as short-answer instead?" CTA so the instructor isn't stuck staring at a spinner.

    R4. Speculative pre-generation

    Effort: 4–6 h Risk: doubles LLM spend per detection Gain: perceived 0s latency

    Fire generate-mcq-options the moment a candidate enters pendingCandidate state — before the instructor confirms. By the time they click "Send", the response is cached. Cancel the request via abort if they dismiss instead.

    R5. Stream MCQ to the client

    Effort: 1–2 days Risk: tool-call streaming is fiddly Gain: perceived 50% reduction

    Lovable gateway → Gemini supports streaming. Pipe partial deltas through the edge function via SSE. Render options as they arrive. Doesn't reduce real latency, but the spinner stops being a wall.

    R6. Validate first, generate once

    Effort: half day Risk: requires rewriting the validator into the prompt Gain: eliminates retry path entirely

    Push the deterministic validateAnswer logic into the prompt as a self-check the model must run before emitting. Removes the second-call tax that costs you 20–60s on the >30% of questions that fail validation.

    5. Issue B — root-cause hypotheses, ranked

    Long sentences with breath pauses get finalized mid-sentence by Deepgram. The detector then sees fragments, each of which fails one or more gates (no "?", below min word count, no interrogative trigger).

    1. Endpointing too aggressive. Deepgram's default endpointing finalizes after ~10ms of silence. A natural sentence-internal pause (300–600ms) trips this. Your long question gets cut into two finals: "If a cell has a high surface-area-to-volume ratio." + "What advantage does that give it?"
    2. No use of UtteranceEnd events. Deepgram emits an UtteranceEnd event after a longer silence window (configurable via utterance_end_ms). That's the right boundary for "speaker stopped talking," not is_final.
    3. Per-chunk detection. checkUtterance() runs on each final independently. It never sees the joined sentence even if you fix Deepgram, unless you buffer client-side.
    4. The first fragment ends in . instead of ?. Even with the new fallback regex, extractQuestions() requires a ? to return anything. The first fragment is silently discarded.

    6. Issue B — diagnostic steps

    D5. Log raw finals with timing

    In handleTranscript(), log every final with start/end timestamps and the silence gap since the previous final:

    console.log(JSON.stringify({
  evt: "dg.final",
  text: transcript,
  end_ms: data.duration ? Math.round(data.start * 1000 + data.duration * 1000) : null,
  gap_ms: this.lastTranscriptTime ? Date.now() - this.lastTranscriptTime : null,
}));

    Have someone deliberately ask a long sentence with one breath pause. The logs will show whether you get one final or two.

    D6. Inspect the WebSocket URL Deepgram is being called with

    The relay (likely a separate Supabase function or Fly.io app — not in this repo) builds the Deepgram URL. Find it and check whether endpointing, utterance_end_ms, interim_results, and smart_format are set. Typical good values for live lecture: endpointing=500, utterance_end_ms=1500, interim_results=true, smart_format=true, punctuate=true.

    D7. Test with a known sentence

    Pre-record the surface-area-to-volume sentence with a natural pause and play it into the mic 5×. Note how often it arrives as one final vs split. That gives you a baseline to measure against after any fix.

    7. Issue B — remediation options

    R7. Tune Deepgram endpointing

    Effort: 15 min (relay config) Risk: low Gain: catches most natural pauses

    Add endpointing=500 and utterance_end_ms=1500 to the Deepgram WSS URL in the relay. Sentences with sub-500ms gaps will stay as one final.

    R8. Use UtteranceEnd as the detection trigger

    Effort: 2–3 h Risk: low Gain: structurally correct

    Buffer all incoming is_final chunks. Only call checkUtterance() on the joined buffer when the UtteranceEnd event arrives (or after trailingSilenceMs elapses with no new data). This is what Deepgram designed those events for.

    R9. Client-side rolling buffer + interrogative recall

    Effort: 1–2 h Risk: false positives if not bounded Gain: complements R7/R8

    Keep a 15-second rolling buffer of recent finals. Whenever a new chunk ends with ?, run extractQuestions() on the joined buffer, not just the new chunk. Clears on long silence or after promotion.

    R10. Accept "?-implied" pre-fragments

    Effort: 1 h Risk: high false-positive rate Gain: catches edge cases R7+R9 miss

    If a final ends in ? and the previous final ended in . within 2 s and starts with a conditional ("If…", "When…", "Suppose…"), treat them as one question. Powerful but trips on natural classroom speech — only do this if R7+R9 still leave gaps.

    8. Recommended sequenced plan

    If you do nothing else, do these three in this order. Each is small, measurable, and de-risks the next.

    OrderActionWhy nowStop here if…
    1 D1 + R1 + R2: add timing logs, fix the model typo, swap primary to Flash 30 minutes of work. The typo and Pro-default explain most of the 90s. Logs prove it. MCQ latency drops below 10s — ship and move on.
    2 D5 + R7: log finals, raise endpointing and utterance_end_ms on the relay Lowest-effort path to keeping long sentences whole. No client code change. Long sentences arrive intact in >80% of cases — ship.
    3 R8 or R9: switch detection to UtteranceEnd or add the rolling buffer Belt-and-suspenders against the cases R7 still misses (pauses >500ms). R9 is faster to ship; R8 is structurally correct. Use R8 if you're investing in this long-term, R9 if you need it this week.
    4 (optional) R4: speculative pre-generation on pending candidates The "feels instant" win. Only worth it after the easy wins above stabilize latency below 10s. —
    5 (optional) R6: fold validator into the prompt Removes the retry tax if >30% of MCQs are failing validation today. D4 shows <10% rejection rate — skip.

    9. Pre-mortem — what could still go wrong?

    • Flash quality regression. Some MCQs that 2.5 Pro got right may now be wrong with Flash. Mitigate: keep Pro on the validator-rejection retry path so weak first attempts get a second chance. Track validator rejection rate before/after as your canary.
    • Endpointing too high → questions arrive late. If you set endpointing=800, you add up to 800ms of latency to every detection. Stick to 500ms unless you see chunking still happening.
    • Speculative pre-gen doubles your LLM bill. If most pending candidates get dismissed (rhetorical / instructor changes mind), you're paying for thrown-away generations. Mitigate: only pre-generate after the pending candidate has survived 500ms of trailing silence.
    • Rolling buffer fires on the wrong question. If you concatenate too aggressively, you'll detect a question that spans two unrelated thoughts. Mitigate: clear the buffer on any sentence-final punctuation followed by >3s silence.
