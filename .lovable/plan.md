## Goal

Make Question on Deck work when the instructor's format preference is **Coding** — for both styles (Simple check-in and Full LeetCode-style problem). Today the on-deck UI silently coerces coding into "short answer" because its prop types and PreviewPanel only know about MCQ / Short Answer / Poll. We also need to make sure conversational coding prompts ("How do you create a variable…", "Can you print hello world") aren't suppressed by the passive detector.

## Scope

Frontend (on-deck wiring + preview UI) and a thin generator endpoint. Backend `format-and-send-question` already accepts `coding` and `coding_simple` — we just need to send the right payload from the on-deck Send Now.

## Changes

### 1. Widen format types end-to-end
- `src/components/instructor/LectureTranscription.tsx`: stop casting `question_format_preference as 'multiple_choice' | 'short_answer' | 'poll'`. Add `'coding'` to the union. Also fetch and store `coding_question_style` ('simple' | 'full') alongside it.
- `src/components/instructor/LiveCopilotHero.tsx` and `src/components/instructor/QuestionOnDeck.tsx`: extend `formatPreference` / `suggestedType` to include `'coding'`. Pass `codingStyle` through `LectureTranscription → QuestionOnDeck`.

### 2. PreviewPanel — coding branches
In `QuestionOnDeck.tsx` `PreviewPanel`, add two new render modes driven by `effectiveFormat === 'coding'` + `codingStyle`:
- **Simple check-in** (`codingStyle === 'simple'`): single editable "Expected concept / answer" textarea (same shape as short answer, label changed). Generated by reusing `generate-expected-answer` with a coding-aware system prompt hint.
- **Full problem** (`codingStyle === 'full'`): editable fields for Problem statement, Function signature (name + params + return type), Examples, Constraints, Starter code, Expected solution. Generated by a new edge function (see §3). Header label shows "Coding" with the Code icon.

The "Regenerate" button works for both. Loading state reuses the existing skeleton.

### 3. New edge function `generate-coding-preview`
Thin wrapper around the `generateCodingQuestion` logic already used inside `supabase/functions/format-and-send-question/index.ts`. Accepts `{ question_text, source_transcript?, prior_context?, style: 'simple' | 'full', language? }`. Returns either `{ expected_answer }` for simple, or `{ problem, function_name, parameters, return_type, examples[], constraints[], starter_code, expected_solution, language }` for full. Pulls instructor's preferred language from `profiles.preferred_programming_language` when not provided.

(Splitting it out avoids forcing the on-deck UI to call `format-and-send-question` just for a preview.)

### 4. Send Now payload
Extend `OnDeckSendData` in `QuestionOnDeck.tsx`:
```ts
type: 'multiple_choice' | 'short_answer' | 'poll' | 'coding';
codingStyle?: 'simple' | 'full';
codingPayload?: {
  problem?: string;
  function_name?: string;
  parameters?: string;
  return_type?: string;
  examples?: string[];
  constraints?: string[];
  starter_code?: string;
  expected_solution?: string;
  language?: string;
};
```
The Send Now path in `LectureTranscription.tsx` already invokes `format-and-send-question`. Add:
- `suggested_type`: `codingStyle === 'simple' ? 'coding_simple' : 'coding'` when type is coding.
- Forward `codingPayload` so the backend can use the pre-edited preview instead of regenerating.

### 5. Backend acceptance of pre-generated coding payload
`supabase/functions/format-and-send-question/index.ts` currently regenerates coding via `generateCodingQuestion`. Add a `pre_generated_coding` branch: when present, skip the LLM call and use the supplied fields directly (mirrors the existing `hasPreGeneratedOptions` path for MCQ). For simple style with only `expected_answer`, wrap it the same way the inline simple branch does today.

### 6. Detection reliability for coding-shaped prompts
`src/hooks/usePassiveQuestionDetection.ts`:
- Lower `minTranscriptConfidence` default from `0.8` to `0.55` (matches the looser deepgram filter we already pushed). Keeps the "first utterance often comes in at 0.6–0.75" failure from killing the candidate before it ever reaches on-deck.
- Add an explicit trigger pattern for imperative coding-style asks that don't start with WH-words: `^(can you|could you|please|let'?s|show me|write|print|create|implement)\s+\S+` so "Can you print hello world?" and "Write a function that…" register even without a terminal "?" sometimes dropped by Deepgram. (Still gated by the rhetorical blocklist and word count.)
